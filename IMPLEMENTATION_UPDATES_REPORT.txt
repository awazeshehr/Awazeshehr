**2. Semantic Analysis Flow (Sentiment Analysis)**
- **Goal:** Automatically analyze complaint text to classify sentiment (Positive, Neutral, Negative) for prioritization.
- **Workflow:**
  1.  **Input:** Citizen submits complaint text via React Frontend.
  2.  **Processing:** Backend receives text and triggers Sentiment Analysis.
  3.  **Analysis Layer:** 
      - **Model:** Pre-trained NLP Model (Python-based).
      - **Tools:** Python (VADER, TextBlob, or BERT/Transformers).
      - **Logic:**
        - Analyze text.
        - Assign Sentiment Label (Positive, Neutral, Negative).
        - Assign Priority Score (e.g., Negative + Keywords = High Priority).
  4.  **Storage:** Store `sentimentLabel` and `sentimentScore` in the Complaint database.
  5.  **Output:** Dashboards display sentiment trends, highlight "Angry/Negative" complaints for immediate attention.

- **Architecture Integration:**
  - **Frontend (React):** Visual indicators for sentiment (Red/Yellow/Green badges).
  - **Backend (Node.js):** Spawns a Python child process or calls a Python microservice to process text.
  - **Database (MongoDB):** Schema update for `sentiment` field.

- **Example Scenario:**
  - *Complaint:* "The garbage has not been collected for 10 days and no one responds."
  - *Analysis:* Negative Sentiment.
  - *Action:* System flags as **High Priority**.

**3. Host BERT Complaint Classifier Online (Option A: Remote Microservice)**
- **Goal:** Ensure complaint classification never falls back because of missing local Python/Torch dependencies by running the BERT classifier on a hosted platform and calling it via HTTP from the Node.js server.

- **Why needed (current issue):**
  - Local `classify_complaint_bert.py` requires `torch` + `transformers`.
  - If the server machine cannot run these (or has incompatible Python), backend falls back to heuristic classification.

- **Target Architecture:**
  1) **Python NLP Microservice (FastAPI)** loads `bert-base-uncased` once at startup and exposes:
     - `GET /health` → `{ ok: true }`
     - `POST /classify` → `{ category: string, confidence: number }`
  2) **Node.js Backend** calls this microservice over HTTP for classification.
  3) **Fallback policy (recommended):** If the microservice is down/unreachable, backend falls back to heuristic to avoid blocking complaint submission.

- **Implementation Steps:**
  1) Create a separate Python service repository (or a `server/nlp-service` folder) containing:
     - FastAPI app (`app.py`) + `requirements.txt`
     - Prototype-similarity classifier logic currently in `server/scripts/classify_complaint_bert.py`
     - Dockerfile for deployment
  2) Deploy the service to a platform that supports Docker and long-running APIs, e.g.:
     - Google Cloud Run (recommended), Render, Railway, Fly.io, AWS ECS/Fargate
  3) Add an environment variable to Node backend:
     - `BERT_SERVICE_URL=https://<your-service-domain>`
  4) Update backend classification flow in `server/services/complaintClassifierService.js`:
     - Try remote call first (`POST ${BERT_SERVICE_URL}/classify`)
     - On success: return `{ category, confidence, source: 'bert-remote' }`
     - On failure: fallback to `{ category, confidence, source: 'heuristic' }`
  5) Add monitoring/verification:
     - Log `source` (`bert-remote` vs `heuristic`) for debugging
     - Health-check endpoint and platform uptime monitoring

- **Acceptance Criteria:**
  - With `BERT_SERVICE_URL` configured, complaint classification uses `bert-remote` for valid requests.
  - Heuristic fallback occurs only when the remote service is unavailable.
